# 定时屏幕观察未响应：定位与修复

## 已获取的证据

- Windows Application 日志于 2026-10-18 21:14:03（UTC+8）记录 `Application Hang / 1002`，对应 `traybuddy.exe`，并有 WER `AppHangB1 / 1001`。这些记录说明进程未响应后被关闭；未找到同一时段的桌宠访问违规崩溃事件或可用崩溃转储。
- 用户反馈手动屏幕观察正常，定时观察运行期间出现问题。检查时自动观察开启，周期为 300 秒。
- 原 AI 模块没有独立阶段日志。现有 DSH 日志不包含本次观察流程，不能据此断言模型请求或截图失败。

## 明确存在的死锁

`Companion::allowed()` 在持有 `AppState.storage` 互斥锁时调用 `window.is_visible()`。安装版本的 Tauri runtime 在后台线程调用此 getter 时，会给界面线程发送消息，并通过通道等待界面处理结果。

定时循环先排入一次界面线程的输入窗口跟随任务，再执行观察条件检查。因此可能形成以下等待链：

1. 后台定时线程持有共享设置锁，等待界面线程完成窗口查询。
2. 界面线程处理已排入的窗口跟随任务，需要读取同一把共享设置锁。
3. 两个线程互相等待，界面失去响应，最终表现为 Windows AppHang。

手动观察不一定遇到相同的消息队列时序，因此手动成功不能排除此问题。此等待链能由代码和 runtime 实现直接证实，与本次 WER 记录吻合；由于没有当时的进程转储，不声称已经还原唯一的线程现场或排除所有其他潜在问题。

## 修复

- 新增独立的访问条件检查：先在短锁范围内读取允许条件，释放锁后再调用窗口查询。
- 所有经过该入口的观察检查共用修复，保持角色、免打扰、锁屏与显示条件不变。
- 不通过关闭自动观察、延长周期或移除可见性检查规避问题。
- 增加 `companion/diagnostics.log`：记录定时触发、允许条件检查、截图、识图、回复、翻译、合成和请求结束等阶段。
- 日志只接受固定阶段名称与数字/布尔字段，不记录窗口标题、截图、聊天原文、回复、密钥或 bank 身份。当前日志达到 256 KiB 后轮换，最多保留当前和前一份日志。
- 用户设置、密钥、对话记录、Hindsight 身份与所有 bank 均未被修改。

## 验证

后端相关测试 15 项通过，真实 Hindsight 可选测试未运行。其中新增回归测试用独立线程和消息通道连续模拟 20 次“后台查询等待界面、界面读取共享设置”的时序，并确保界面能立即重新获取锁；用 `try_lock` 和有界等待防止测试本身无限卡住。同时验证关闭观察/常规聊天的条件行为，以及诊断日志格式和轮换。

另以不包含 Tauri、截图或网络的最小测试程序作对照：恢复旧的持锁作用域时，同一回归明确失败并报告界面无法获取设置锁；使用修复后的作用域时，20 次往返全部通过。这验证了测试能够捕获原来的等待冲突。

桌面自动化工具当前返回 `codex app-server exited before returning response 1`，不能把上述线程回归测试描述为新程序已经完成连续真实截图播报实测。新包的成品检查可独立验证生产模式和内置页面。

## 后续排查

切换到修复版后，保留原周期即可观察。若仍有异常，优先提供发生时间和 `companion/diagnostics.log`、`companion/diagnostics.previous.log`；日志中阶段之间的缺口可帮助区分条件检查、截图、模型、语音及本地记录阶段。旧版进程需要退出后再运行修复版，单实例机制不能让正在运行的旧程序自动获得修复。
