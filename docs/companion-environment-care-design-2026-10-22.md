## 1. 目标与范围

将时间、日期、地点、天气和节日资料统一交给应用级环境服务管理；在事实可靠、时机合适时，由程序随机安排一句低优先级关怀。用户主动输入、提问、阅读和播放回复始终优先。

两个核心约束：

1. **数据有效期**：过时、未知或地点不匹配的天气，不能支持“现在下雨”等主动提醒。获取成功不等于观测新鲜。
2. **候选有效期**：适合早上说的提醒不能无限排队到下午；发送前重新核验，不适合就丢弃。

必须按顺序实施：**A. 统一数据及有效性检查并迁移全部旧入口 → B. 实现候选、过期与去重 → C. 接入随机时机、台词和交互优先级**。A 阶段可以单独上线修复旧天气提醒，B 未完成前不启用新关怀，C 完成后才开放新开关。

首版由程序和预设台词完成，不调用对话模型、TTS 服务、网页搜索或其他智能体。后续若增加模型措辞生成，仍须经过同一有效性与优先级检查，但不属于本稿实施范围。

首版新增关怀：雨天带伞、晚间休息、元旦及春节祝福。既有 Ema 冷热、下雪等天气台词通过兼容适配纳入有效性和呈现限制，不扩展新的气象风险判断。该功能不推断用户疲劳、是否出门、是否放假或连续工作时长。

位置能力纳入 A 阶段的共享数据建设：支持固定关注城市，或在用户允许后按“设备定位 → 备用城市 → IP 粗定位”选择位置。首版采用一次读取与有限刷新，不连续追踪、不保存移动轨迹。定位改善地点匹配，不能替代天气观测时间、来源分辨率或提醒有效期检查。

## 2. 当前架构与问题定位

### 2.1 已有能力

- `environment.rs` / `environment_runtime.rs`：本机时间、IP 粗略位置、wttr.in 天气、静态缓存和初始化更新事件。
- `StateInfo`：支持公历月日范围、跨午夜时间范围、温度和天气码限制。
- `state_runtime.rs`：按持久状态的间隔、概率及候选权重随机触发。
- Ema `manifest.json`：idle 默认间隔 600 秒、概率 0.75，候选已有 `rain`、`cold`、`hot`、`snow`、`long_time` 等；`night` 也有对应台词。
- `Companion` 和 `presentation.ts`：已有请求取消、忙碌、阅读及语音状态，可作为主动交互状态的来源。

### 2.2 陈旧提醒为什么会发生

1. 初始化主要在启动时拉取一次天气，没有由统一服务拥有的持续刷新任务。
2. `EnvironmentManager::get_weather()` 虽然检查 30 分钟缓存，但 `get_cached_weather()` 不检查；`commands::get_weather_info()` 只要已有缓存就直接返回，绕过前者。
3. `state_runtime.rs`、`StateLimitsContext` 和 `companion/capabilities.rs` 均直接取缓存；天气筛选主要检查天气码/文字，不检查观测时间和地点。
4. `WeatherInfo` 没有观测时间、有效期、来源和地点；无法区分“刚取到早上的旧观测”与“刚取到当前观测”。
5. IP 位置首次获取后长期缓存，失败还会按时区推算坐标；没有位置年龄、来源质量或权限状态。天气查询优先采用城市名，新增设备坐标后若不迁移该入口，仍可能退化为同一城市级查询。

所以，下午可能仍将早上的雨天状态视为当前事实，再随机命中带伞台词；不需要存在一个排队数小时的消息，也会出现用户描述的问题。不得仅通过调低触发概率、缩短随机间隔或修改台词来掩盖数据缺陷。

## 3. 总体架构与所有权

### 3.1 应用级服务

新增由 Tauri `manage` 注册的两个独立服务：

- `EnvironmentService`：拥有环境数据、位置模式与适配器、版本、刷新生命周期和有效性规则。统一管理 Windows 定位、城市选择、IP 兜底与天气请求；无模型密钥、无对话 bank，不依赖 `Companion::ensure_ready()`。
- `CareService`：订阅环境和交互状态，管理候选、随机调度、呈现租约及提醒记录。无天气网络客户端，不直接读取原始天气缓存。

二者在 `AppState` 和窗口创建前完成注册；后台任务只启动一次。退出时取消各自任务。AI 配置损坏或未配置密钥不影响时间读取和预设关怀服务的初始化。

### 3.2 数据流

环境适配器获取数据，经过验证后原子发布环境版本；聊天、Mod 状态、关怀、调试页读取同一个权威快照。关怀将环境变化转换为短期候选，再经过交互检查和呈现检查。

前端事件只是“数据变了”的通知，不是事实的永久副本；数据在没有新响应时也可能自然过期。实际使用时始终由后端重新判断当前有效性。

不把整个快照每秒复制到所有窗口；时间在读取时采样，天气、地点和日历按相关版本发布。候选绑定相关依赖版本，不能因为时钟秒数更新而全部失效。

### 3.3 并发与锁

网络请求、城市解析和日历文件加载不在主 UI 线程执行。先复制需要的配置和快照，再释放锁进行异步操作，最后按请求及地点版本决定是否提交。

Windows 首次定位授权是例外的入口要求：通过应用前台的设置操作，在 UI 线程发起系统权限申请；不得同步阻塞 UI 等待授权或定位结果。取得访问资格后的定位读取由平台适配器异步完成。环境读取、聊天或关怀定时器不能自行弹出权限申请。

环境锁与 `storage → resource_manager → state_manager` 原有锁序不嵌套。`StateLimitsContext::prefetch()` 在取资源/状态锁前取得已经验证的数据副本；呈现前的二次检查也不能在持有状态锁时调用窗口同步方法。

## 4. 共享数据合同 ENV-CARE-1

### 4.1 环境视图

`EnvironmentSnapshot` 至少包含：

- `schema_version=1`、`environment_revision`。
- `clock`：本次读取的 UTC 时间、本地日期、时间、星期、时区标识或偏移及 `clock_revision`。
- `location`：位置模式、当前选定地点、来源、时效/可信状态、降级原因和 `location_revision`；原始坐标按消费者投影，不向所有窗口和模型广播。
- `weather`：最近天气数据、事实元数据、当前有效性和刷新状态。
- `calendar`：本地日期对应的节日、地区、数据版本和覆盖状态。

单个快照在一次返回时自洽；网络请求完成后再采样本次返回的时间，不能把请求发出前的时间当作当前时间。

### 4.2 天气记录

`WeatherRecord` 至少包含：

- 原有天气状况、天气码、温度、体感、湿度和风速，均验证类型、单位与有限数值。
- `provider_id`、`location_key`、`location_revision`、服务实际解析的地点（可空）。
- 请求采用的城市标识或天气查询区域键，以及服务实际匹配区域的核验结果；按坐标请求不能只凭 HTTP 成功认定地点正确。
- `observed_at_utc`（可空）、`received_at_utc`、当前进程内的接收单调时钟标记。
- `evidence_kind=current_observation`；首版不将日汇总或预报混入当前实况。
- `observation_quality=known|unknown|invalid`、`weather_revision`。

`WeatherValidity` 是读取时计算的结果，不由缓存文件永久宣称：

- `fresh`：满足对应消费者的地点、年龄、时间和数据质量要求。
- `stale`：有数据但超过使用期限。
- `unverified`：地点或观测时间无法可靠核验。
- `unavailable`：没有可供使用的数据。

另提供 `refresh_state=idle|refreshing|backoff|disabled` 和限定错误码。刷新中不等于数据新鲜，刷新失败也不等于必须丢弃尚在有效期内的数据。

### 4.3 地点

#### 4.3.1 模式与来源顺序

`location_mode=fixed_city|automatic`，两种模式的行为必须明确区分：

- `fixed_city`：始终使用用户明确选择的 `fixed_city`，不调用设备定位或 IP 定位来覆盖。未设置或城市标识无效时，返回地点不可用并提供修正入口，不暗中切换模式。
- `automatic`：先使用用户允许且质量合格的 Windows 设备位置；不可用时使用已明确设置的 `fallback_city`；仍不可用且允许 IP 兜底时，才获取 IP 粗定位。所有来源都不可用则暂停天气相关功能，不继续按时区猜测坐标。

固定与备用城市均用可消歧的规范城市标识、地区层级及显示名保存；输入的同名城市须完成选择，不能仅凭一段自由文本确定地点。城市中心坐标是天气查询参考点，不冒充设备测得坐标。不同来源不做坐标平均或投票推算；每次选择一个可用来源并记录降级原因。

“位置不可用”与“天气请求失败”分别处理。已确定地点但天气接口失败，不触发位置降级、不改用另一城市；只执行天气退避与失效规则。备用城市代表用户关注意图，不保证用户仍身在当地，界面必须标明“正在使用备用城市”。

#### 4.3.2 位置记录与状态

`LocationSelection` 至少包含 `mode`、`location_key`、规范城市/地区标签、`source=manual_fixed|device|manual_fallback|ip_approximate`、确认/质量状态、降级原因及 `location_revision`。经纬度必须在合法范围且为有限值。

`LocationFix` 另记录来源测定时间 `positioned_at_utc`、接收 UTC/单调时间、设备水平精度 `accuracy_m`（不适用时为空）、请求代次和当前有效期。IP 城市返回的中心坐标没有设备测量精度；不得填入一个虚构的米级精度。来源测定时间未知的设备坐标不被当作当前有效位置。

分开表示应用配置 `device_location_enabled`、Windows 访问状态 `not_requested|allowed|denied|unavailable` 和读取状态 `idle|locating|backoff|disabled`；应用开关开启不等于系统授权成功，读取中也不等于已有有效位置。

`location_revision` 表示会改变天气依据的选择版本；另以 `location_record_revision` 表示同地点的新定位记录。质量合格的新记录仍落在同一规范天气查询区域时，只更新记录与有效期，不因坐标微小抖动清除天气、重建雨天事件。

#### 4.3.3 关怀准入与措辞

天气关怀的可靠位置依据限于：用户明确选择的固定/备用城市、用户允许且通过质量及年龄检查的设备定位，或用户确认过的当前 IP 城市。服务返回地点与请求的绑定关系仍须可靠；重名无法消歧、区域不匹配时不能触发。

IP 结果始终标为近似，不自动升级为精确所在地。首次估计或估计城市变化时，在设置/天气区域提供非阻断确认入口；未确认可展示带城市与“根据网络估算”标记的天气预览，但 `care_current`、`legacy_weather_trigger`、`dialogue_current` 不接收该结果作为当前事实。确认只绑定规范城市标识；下次估计变为另一城市不能继承确认。确认 IP 城市不会自动改写固定或备用城市，保存为常用城市需明确操作。

用户主动启用设备定位并完成系统授权后，合格位置不要求每次再次确认城市。系统返回坐标仍须通过精度、时间和天气地点映射检查；不以“已授权”替代事实核验。

“关注城市”不等于证明用户身在当地。固定、备用或 IP 城市关怀采用“上海的天气资料显示有雨，准备出门的话可以带把伞”等条件表达；设备定位也不据此声称用户正在出门或窗外必然下雨。不能把单纯时区推算坐标用于天气或关怀。

#### 4.3.4 地点变化与设置失效

天气查询区域、模式、来源使用资格或城市确认状态改变时，递增相关选择/配置版本，先取消依赖旧依据的候选和呈现租约，再计算新选择并刷新天气。旧地点请求迟到返回不得覆盖新地点。

关闭设备定位或系统撤销权限时，立即取消/失效设备请求，撤销设备坐标作为当前位置的资格，再按当前模式与开关选择备用来源；关闭 IP 兜底同样使在途 IP 结果失效。底层调用无法立即停止时，代次检查必须阻止其结果提交。不得等待请求成功后再执行关闭，也不得复用关闭前坐标绕过开关。

同地点仅时间戳更新不机械增加 `location_revision`；已经确认的同一区域天气能否继续使用，由现有地点绑定、年龄与来源使用资格重新判断。首版模式或来源资格变化保守撤销旧天气的当前使用资格，即使显示城市名称相同也须按新依据核验，不从旧坐标续用。

### 4.4 消费者合同

定义 `WeatherUse`，至少区分 `care_current`、`legacy_weather_trigger`、`dialogue_current` 和 `diagnostic`。

- 关怀和旧天气触发只接收适用的 `UsableCurrentWeather`，该类型只能由有效性检查成功构造。
- 对话若没有可靠当前天气，只能拿到状态说明或明确带时间的旧资料，不能拿到无标记的陈旧天气 JSON。
- 调试页允许查看旧记录，但同时展示地点、观测时间、接收时间、年龄、刷新状态及不可用原因。

`dialogue_current` 使用与当前关怀相同的地点和年龄门槛；如需讨论历史天气，必须显式提供原时间及“历史资料”标记，不能绕过当前资料合同。

前端不能自行传 `fresh=true`、`observed_at` 或 `now` 作为事实，判断权在后端。接口中出现的 `now` 只来自内部可注入 Clock，测试可以替换 Clock，生产命令不得信任前端时间。

## 5. 时效策略与系统时间

### 5.1 首版内部参数

以下参数可在编码后根据数据源实测调整，但不可为提高触发率静默放宽：

- 活跃且可见时天气目标刷新间隔：10 分钟。
- 当前天气本地接收缓存年龄上限：15 分钟。
- 关怀及旧天气触发允许的观测年龄上限：30 分钟。
- 对来源时间轻微超前的容忍：最多 2 分钟；超过则 `invalid`。容忍不用于延长旧观测寿命。
- 后台天气请求总时限：8 秒，连接时限不超过 3 秒，响应解压后上限 1 MiB。
- 失败退避：1、5、15 分钟，后续最多 30 分钟；成功重置。每次到期只发一次请求，不在一次刷新内部立即重试。

关怀可用需同时满足：地点可靠且版本一致、数据格式有效、观测时间已知、观测年龄未超限、接收缓存年龄未超限，以及没有恢复/时钟异常导致的待核验状态。

天气记录本身的概念有效期为：

```text
expires_at = min(observed_at + 30min, received_at + 15min)
```

到达截止时间即不可用，即 `now >= expires_at` 时拒绝。进程内接收年龄以单调时间计算；观测年龄结合 UTC 及时间异常检测计算，不能只相信墙上时钟。不得使用 `now - cache_time` 的无保护无符号减法。

使用天气时还须满足位置依据有效；天气关怀候选的截止时间不得晚于当前位置有效期。固定/备用城市不按定位年龄过期，但仍受配置、城市解析与确认状态约束。

### 5.2 数据源能力门槛

当前 wttr.in 适配器需保留原响应中的可用观测及地点信息，并验证时间格式、时区和跨午夜语义。若来源只给无日期的时间，不能自动拼接“今天”来伪造完整观测时间。

本轮未实测该源能否在目标地区持续提供 30 分钟内、带可靠时间的实况。编码 A 阶段必须验证；不能满足时，就暂停天气关怀并在设置中说明原因，或单独更换能满足合同的适配器。不能以最近接收时间替代观测时间。

“新鲜”只表示资料在约定年龄内，不保证现实天气没有在观测后变化。普通关怀使用“天气资料显示……”等与证据相称的表述。

### 5.3 时钟变化与恢复

日期和时段按本机时区判断；在每次使用和跨日时重算，不缓存早上的“当前时间”供下午使用。时区变化递增 `clock_revision`，重建日历视图，取消受影响候选。

结合系统恢复通知、调度长间隔、UTC 与单调时间差变化识别休眠恢复或明显时钟跳变。进入待核验时：取消临时候选和呈现租约；天气须刷新成功且合格后才重新可用；关怀进入 120 秒安静期。

夜间冷却用单调时间，跨重启去重用持久记录。发现持久记录时间明显在未来时采取保守抑制，不把异常记录立即当作旧数据清除。本设计不联网校时，也不保证发现设备时钟本身所有错误。

### 5.4 位置时效与首版内部参数

以下是待 A 阶段验证的初始参数，不是对 Windows 定位精度或速度的保证：

- 自动模式、应用可见且未锁屏、访问已允许时，设备位置目标刷新间隔 20 分钟，有效年龄上限 30 分钟；恢复、权限或相关网络状态变化时提前核验。隐藏/锁屏停止周期定位，不补发漏掉的周期。
- 单次设备位置读取等待上限 10 秒；向系统请求的最大缓存年龄为 5 分钟。返回后仍检查实际测定时间，不能因刚接收或参数设置就认定新鲜。
- 设备水平精度初始上限 5,000 米；缺失、非有限、负数、超限或明确为未知的精度不支持设备天气关怀，按来源顺序降级。不得为了命中提醒而伪造精度；边界区域须结合天气服务覆盖核验。
- 定位未来时间最多容忍 2 分钟，采用与天气相同的时钟异常保护。设备位置到期取测定年龄与接收年龄中更早的限制；重复读取同一旧定位不延长测定有效期。
- IP 估计的本地缓存年龄上限 60 分钟；相关网络状态变化时撤销旧 IP 估计的当前资格。仅在自动模式、前两项不可用且 IP 开关允许时刷新；不为检测城市变化在固定模式后台查询 IP。
- IP 请求总时限 5 秒、连接时限不超过 3 秒，解压后响应上限 256 KiB；外部城市解析如有需要，须单独限定预算，不能隐藏无限网络等待。
- 各来源读取合并，手动请求最短间隔 30 秒；定位失败按 1、5、15 分钟退避，后续最多 30 分钟。设备来源不可用时及时尝试允许的备用来源，不阻塞普通聊天或延长一轮关怀等待。

城市粒度和天气查询区域的稳定映射规则在 A 阶段按实际来源确定并测试，不能直接用每次原始浮点坐标字符串作为事件键。位置有效不保证附近每一处天气相同；当前实况也不能替代短时降雨预报，首版不增加“即将下雨”的预报关怀。

## 6. 刷新生命周期与共享接口

### 6.1 接口语义

建议后端接口：

- `read_snapshot(now)`：快速读取并计算当前有效性，无网络等待。
- `current_weather_for(use_case, now)`：返回经过验证的当前天气或带原因的不可用结果。
- `request_weather_refresh(reason)`：请求异步刷新，返回共享结果或进行中状态。
- `request_location_refresh(reason)`：按模式、应用开关及已有系统访问状态异步解析位置；无权发起首次系统授权，不以天气失败为触发理由。
- `subscribe()`：订阅版本变化、数据过期、地点变化和刷新结果。

设置/调试命令可暴露 `environment_get_snapshot`、`environment_refresh_weather`；普通状态筛选只读内存。原 `get_datetime_info` 等命令保留兼容包装，不继续各自创建独立管理器。

### 6.2 一次请求与迟到保护

同一地点版本最多一个天气请求；多个读者加入同一次结果，不重复发请求。不让某个读者取消等待就取消其他读者仍需要的共享刷新。

每次请求绑定 `location_revision`、天气配置版本和请求序号。地点改变、禁用网络天气或切换来源后，旧请求结果必须丢弃；旧观测不能覆盖已接受的新观测。重复获得同一观测可以更新接收记录，但观测有效期仍锚定原观测时间。

设备与 IP 位置请求还绑定 `location_config_revision`、访问代次及来源请求序号。应用关闭对应开关、切换模式或系统撤销权限时先增加代次；任何旧结果均不能重新启用位置或触发天气刷新。

请求开始、结束和失败均不持有跨网络的应用状态锁。更新后发布一致快照；过期时也发布有效性变化，不要求一定有新网络响应才通知读者。

### 6.3 自动与手动刷新

网络天气启用时，在启动、有效地点变更、恢复后启动一次刷新；角色可见且桌面未锁定时按 10 分钟目标更新。长期隐藏或锁屏可暂停周期请求，恢复时不补发漏掉的周期。

尚无有效位置时，先由允许的位置来源异步确定；天气定时器只提出刷新需求，不再自行调用 IP API。位置解析中读取快照立即返回状态，聊天、Mod 和关怀均不等待定位完成。已经有有效位置时可以直接按其刷新天气，不必每次天气查询都再定位。

手动刷新与后台刷新合并，最短请求间隔 30 秒，防止连续点击。网络天气关闭时不发自动或手动请求，按钮说明当前关闭状态，同时撤销天气关怀及旧天气触发的使用资格；旧记录只供带标记的诊断查看。失败只产生安静的设置/诊断状态，不弹关怀或覆盖用户正在进行的对话状态。

### 6.4 Windows 定位与来源适配

新增 `DeviceLocationProvider`、城市目录/解析器和 `IpLocationProvider`，由位置选择策略统一调度。Windows 后端使用 `Windows.Devices.Geolocation`；项目已使用 `windows` 0.58，编码时增加所需 feature 并验证线程和运行时支持，不通过聊天模型或网页搜索取得位置。

用户在前台设置中开启“允许使用设备定位”或主动重试授权时，才进入系统访问申请流程。申请须从 UI 线程发起；用户拒绝后记录访问状态，定时器不重复申请，可提供打开 Windows 定位设置的入口。应用开关仅控制桌宠，不修改系统全局定位设置。微软区分打包与未打包应用的能力声明要求，当前 Tauri NSIS 安装形态须独立实测，不能把 Tauri capability 配置等同于 Windows 授权。[Windows 定位接入说明](https://learn.microsoft.com/en-us/windows/apps/develop/maps-and-location/get-location)

系统定位可能依赖多种可用信号，成功不保证高精度；使用返回精度与测定时间做质量检查。[定位精度说明](https://learn.microsoft.com/en-us/uwp/api/windows.devices.geolocation.geocoordinate.accuracy?view=winrt-26100) 读取可指定缓存年龄和等待上限，但仍须检查实际返回时间。[位置读取接口](https://learn.microsoft.com/en-us/uwp/api/windows.devices.geolocation.geolocator.getgeopositionasync?view=winrt-26100)

仅做一次读取和有限周期刷新；可订阅系统状态变化以处理撤权/不可用，不启用持续位置追踪作为首版前提。调用失败用受限错误码返回，不能使整个环境服务或关怀循环退出。系统平台不支持时走允许的备用来源。

设备来源按合格坐标查询天气，不再优先退回自由城市名称；固定/备用城市按规范城市标识映射到来源支持的查询。适配器核对实际返回区域，不能承诺天气源提供定位精度对应的气象分辨率。已有 IP 接口为明文 HTTP，A 阶段须替换/验证满足 HTTPS、超时及响应上限的实现；若无法满足，IP 来源保持不可用，不沿用不合格实现来完成兜底。

## 7. 日历与节日

首版节日目录为元旦、春节：元旦由公历 01-01 规则计算；春节读取随版本发布的年度节日表。年度表首版目标覆盖 2026–2030，构建时按可靠公历农历对照资料核对，并保存来源、版本和覆盖范围；超出覆盖范围返回未知，不由模型猜日期。

香港天文台提供 1901–2100 年公历农历对照表，可作为年度表的核对来源之一。[官方对照资料](https://www.hko.gov.hk/en/gts/time/conversion.htm) 本稿不写入未经逐年核对的春节日期；年度表整理是 A 阶段交付项。

`CalendarSnapshot` 记录 `local_date`、`timezone_key`、`region=CN`、`dataset_version`、`coverage`、当天节日列表。按设备本地日切换显示选定地区的节日，不自动声称用户处于某个法定休假状态。

首版不读取远程节假日接口，不判定调休、补班或用户排班。节日祝福、休息日和工作日是不同概念。日历数据损坏仅抑制受影响节日，不能停用本机时间或整个桌宠。

## 8. 候选模型与生成规则

### 8.1 候选结构

`CareCandidate` 在内存中存在，至少包含：

- `candidate_id`、`kind`、`event_key`、`mod_id`、`mod_revision`。
- 事实依据及相关 `location_revision`、`weather_revision` 或日历日期/版本。
- `created_at`、`not_before`、`expires_at`、优先级、可选台词 ID。
- `state=eligible|scheduled|waiting_idle|offered|expired|cancelled`。

不把候选当作必须送达的通知；不跨重启恢复候选，不无限追加等待队列。同一事件最多一个候选，全部候选总数最多 3 个；过期先清除。

### 8.2 雨天

仅合格的当前实况支持雨天候选。适配器用明确码表把来源天气映射为“可用的降雨依据”，不能靠字符串含“雨”或未知码猜测；“附近可能有雨”不能配绝对的“窗外正在下雨”。码表和台词语义一起测试。

首版事件键：`mod_id + rain + location_key + local_date`。同一地点同一天最多展示一次，另设雨天类别 8 小时滚动冷却，避免跨零点连续提醒。每次接口返回不产生一个新的雨天事件。

候选最长 5 分钟，且不晚于天气与位置依据中更早的有效截止时间；创建后的截止时间不因同区域定位刷新而顺延。天气转晴、变为陈旧/未知、位置到期或地点变化立即取消。当天已提醒过后再次下雨，首版也不再提醒；这是减少打扰的明确取舍，暂不实现降雨过程识别。

候选未显示就过期后，新的合格观测可以重新产生同一未完成事件的候选，但使用新事实和新期限；不能延长原候选，也不能在同一条旧观测上不停重建候选。用来源、地点、观测时间和归一化天气类别构成 observation key；不能用单纯接收次数或 `weather_revision` 递增冒充新观测。

### 8.3 夜间休息

默认时段 23:00–02:00，可配置跨午夜。事件键使用夜间开始日：例如某日 23:00 到次日 02:00 属于同一个 night key，不因过零点再次提醒。

每个夜间最多展示一次。候选最长 10 分钟，且不晚于时段结束；到 02:00 后不补发。未展示的候选过期后，可以在后续新空闲窗口重新产生候选，但不在同一空闲窗口连续重建。只表达时间关怀，不从应用启动时长推断用户工作、疲劳或睡眠情况。

### 8.4 节日祝福

当天第一次适合关怀时产生候选；默认祝福时段 08:00–23:00。事件键包含 Mod、节日 ID、地区和本地日期，每个节日当天一次。

单个候选最长 10 分钟；用户长期忙碌时允许在当天后续新的空闲窗口重新产生候选，但不保留旧消息，不在同一空闲窗口反复抽签。当天结束后丢弃，不在次日补说“今天新年快乐”。

## 9. 频率与随机时机

### 9.1 首版默认值

- 全局展示间隔至少 45 分钟；任意连续 24 小时最多 3 条自动关怀。
- 用户主动交互完成或停止后，保留 120 秒安静期。
- 程序启动、恢复、时区/显著时钟变化后，保留 120 秒安静期。
- 合格候选随机延迟 20–120 秒，只抽取一次；每 30 秒或相关事件到达时评估是否可以推进。
- 同一时刻最多一个关怀呈现租约，无多个关怀排队播放。

随机延迟必须落在候选剩余有效期内；放不下就放弃。全局冷却已知会超过候选有效期时也直接放弃。不能通过每秒重抽概率形成迟早必触发的高频循环。

“新空闲窗口”是从忙碌/抑制状态转为满足安静期的可呈现状态时递增的 `eligibility_epoch`，不是每次 timer tick。夜间与节日按 `(event_key, eligibility_epoch)` 限制候选创建，天气另外按 observation key 限制。

### 9.2 多候选选择

不同关怀均低于用户交互；关怀内部先处理即将失效且未重复的合理候选，同等情况下权重随机。选择后其他候选仍按原有效期过期，不顺延期限。

台词选择应避免连续使用同一变体。随机只作用于时机与表达，不随机决定天气事实、节日日期或是否遵守频率上限。

### 9.3 展示前复核

选中与呈现前至少复核两次：最新事实仍成立、候选未过期、Mod 未变、用户空闲、冷却及限额允许。天气版本变化时重新判断，不因版本号变化机械删除仍成立事实，也不能沿用已不成立的旧文本。

如果新的天气、地点或时钟变化使已经展示的短关怀失效，撤销其剩余展示和未开始的配音；用户主动消息到来时同样撤销。

## 10. 主动交互优先级与呈现租约

### 10.1 交互状态

建立共享的 `InteractionSnapshot`，至少包含：是否正在编辑/中文组合输入、手动请求阶段、正在阅读回复、回复音频、锁屏、免打扰、角色可见、当前 Mod 和 `interaction_epoch`。

输入框只上报编辑活动布尔值和租约，不上报按键或草稿内容。编辑租约按活动续期，窗口销毁或连接丢失后自然失效；不能用一个永远为 true 的失联标记永久阻塞关怀，也不通过全局键盘采集判断用户疲劳。

用户消息提交时先增加交互版本、撤销 care 租约，再执行原对话入口。关怀不设置 `Companion.busy`，不禁用发送、不清除草稿、不改变焦点、不覆盖对话状态文字。

### 10.2 抢占和租约

1. 后端复核后申请短 `CareLease`，包含 `delivery_id`、`care_generation`、`interaction_epoch`、候选和依据版本；待展示租约最长 2 秒。
2. 发出 `care-offer`；渲染层在实际显示前再次检查本地对话/编辑状态、租约版本和取消标记，不能只因收到事件就覆盖气泡。
3. 用户交互在任何阶段发生时撤销 care，并通过独立 `care-cancel` 失效旧代次；不要用会停止用户回复的全局 `companion-stop` 来取消 care。
4. 显示成功后发送 `care-presented` 回执，按 delivery ID 幂等计次。过期或旧代次的 offer、回执和音频不能复活关怀。

用户交互与关怀同时到达时用户获胜。UI 先提交的用户操作不能被迟到 offer 覆盖；已开始的关怀可立即收起，用户不需要先点击停止。

首版不调用新语音 API。若启用经核对的本地预设配音，开始播放前仍须持有有效租约，并遵循全局静音；抢占只停止 care 拥有的音频，不能误停用户正在播放的回复。

### 10.3 台词及来源

新增纯文本短台词或复用语义一致的现有台词，1–2 句；日期、城市等占位符只来自已验证的数据。不能用带“你已经忙很久”含义的旧台词替代只有晚间时间依据的新提醒。

不创造虚拟用户消息，不调用 `Companion::run(...observe=true)` 作为关怀入口，不将 care 伪装成屏幕观察。关怀默认不写入对话 turns、Hindsight 或用户资料；若以后需要“刚才提醒过什么”的会话引用，应另定义来源。

## 11. 旧入口迁移与防重复

### 11.1 A 阶段必须迁移的读者

- `commands/mod.rs`：`get_weather_info`、位置命令和时间命令改为服务包装；已有数据不能再自动跳过检查。
- `companion/capabilities.rs`：使用带日期/地点和有效性的快照；当前天气不可用时明确说明，不注入无标记旧天气。
- `StateLimitsContext::prefetch()`、`StateManager::start_timer_loop()` 和实例限制检查：全部使用 `UsableCurrentWeather`，包括温度判断。
- `EnvironmentDebugger.svelte`：区分获取时间与观测时间，展示状态；刷新按钮真正请求服务，不只是重新读缓存。
- `lib.rs`、`lib_helpers.rs`：统一注册和启动服务，替换独立初始化线程，不重复启动循环。

原裸 `get_cached_weather` 取消公开访问，或作为严格兼容包装只返回有效天气；调试所需旧数据必须显式读完整快照。项目内搜索不得剩下绕过有效性的原始缓存访问。

旧状态预取应携带有效截止时间和可快速核验的天气/地点代次；真正切换天气状态或发出气泡前再检查。可使用原子代次及预取租约避免在持有 rm/sm 时反向取环境或 storage 锁，不能以“已预取”跳过发送前过期检查。

### 11.2 C 阶段接管 Ema 关怀状态

把 Ema 的 `rain`、`night`、`long_time` 及冷、热、雪等关怀类状态通过一张受控映射交给 CareService。idle、login 等任意触发路径都不能绕过映射直接播放这些台词。可以保留素材 ID，不要求改写用户安装的包。

`long_time` 不具备用户连续工作事实依据，停用其原推断式台词或替换为纯时间关怀。`night` 晚间问候若包含休息内容，与 NightRest 使用同一去重键。冷热雪类沿用 Mod 原阈值，但必须使用合格数据，受同一全局频率和呈现租约控制；不增加新健康或风险结论。

普通 idle 动画和非关怀随机内容保留。其他 Mod 在 A 阶段统一修复天气时效；首版新增 CareService 只对 Ema 生效，不向其他角色播放艾玛台词。

不能在原有雨天随机触发之外再叠加一条独立雨天调度。关怀关闭后，Ema 受管关怀状态也关闭，不允许旧路径作为后门继续说；此行为变化需在发布说明写清。

## 12. 配置与持久化

### 12.1 独立配置

在应用配置目录增加两个独立、版本化的配置文件，避免与对话/上下文/搜索设计中的 Settings 迁移冲突：

- `environment/settings.json`，`schema_version=1`：网络天气开关、位置模式及来源开关、城市选择、IP 城市确认和日历地区。
- `care/settings.json`，`schema_version=1`：总开关、类别开关、夜间时段和本地预设配音开关。

环境配置的首版字段至少包括：

- `network_weather_enabled`：网络天气总开关。
- `location_mode=fixed_city|automatic`：位置模式；首次配置默认 `fixed_city`，城市未选择时显示待设置，不据此猜测地点。
- `fixed_city` / `fallback_city`：可空的规范城市记录，分别服务固定模式和自动模式，不从缓存 IP 城市静默生成。
- `device_location_enabled=false`：允许使用 Windows 设备定位；仅自动模式使用。开启后仍须取得系统访问资格。
- `ip_fallback_enabled=false`：允许自动模式在设备位置和备用城市都不可用时，通过 IP 估算城市。
- `ip_confirmed_city_key`：可空，记录用户确认的规范 IP 城市，仅供同城估计核验，不代表设备精确位置。
- `calendar_region`：独立日历地区；不随 IP、设备位置或备用城市自动改变。

网络天气首次迁移默认开启，但位置未设置或来源未获允许时不发天气请求；旧的 IP/时区缓存不迁移为用户确认地点，也不据此自动开启新设备或 IP 开关。发布说明需说明旧的启动 IP 查询改为显式选项。新自动关怀默认关闭，用户开启后无需每条确认；类别默认允许雨天、晚间和节日，预设配音默认关闭。

设置提供“固定城市 / 自动位置”选择及城市选择器。自动模式展示“允许使用设备定位”和“定位不可用时，允许通过 IP 估算城市”两个独立开关，并说明后者仅在没有可用备用城市时使用；固定模式不使用这两个来源，即使保留了开关偏好也不后台查询。

设备开关只控制 Windows 来源；关闭后若 IP 兜底仍开启，界面明确显示其仍可能使用网络粗定位。若未来改用含义更广的“允许自动获取位置”总开关，关闭语义必须同时禁止设备和 IP 获取，不能用一个宽泛标签掩盖不同实际行为。

网络天气关闭时，暂停为天气运行的自动设备/IP 刷新，并撤销天气使用资格；设置中明确发起的单次位置更新仍须遵守各来源开关和权限，不联动天气请求。天气、设备定位和 IP 开关均不影响本机时间读取。系统权限状态是运行时事实，不以配置文件中的布尔值伪造。

首次升级仍可保持原 A 阶段的有效旧提醒；只有 C 阶段正式接管发布后才按新关怀总开关统一控制，并说明默认关闭意味着受管旧关怀不再直接触发。不能在分阶段半成品中提前禁用旧路径却不提供替代设置。

数值预算、年龄和冷却先作为受测内部常量，不在首版设置中提供大量高级滑块。保存原子化，保留备份；损坏时保留原文件，关怀停用或天气不可用，不重置其他应用数据。

新设置区挂在普通桌宠设置中，不依赖 AI 配置成功；显示“天气关怀暂不可用”的具体原因，例如地点未确认、观测时间未知或资料过期，而不是用弹窗反复提示。

位置区域同时展示当前采用的城市/地区、来源、粗略或已确认状态、更新时间及降级原因。定位失败的提示提供修正城市或查看系统设置入口，不反复打断对话、不要求每条天气提醒确认。

### 12.2 关怀记录

使用独立 `care/ledger.sqlite`，不更改 `companion/history.sqlite` 的 schema、turn.source 或专用 bank 身份；不占用其他设计稿已规划的数据库版本号。

记录类型及事件键、delivery ID、角色、必要地点键、展示时间、本地日/night key、台词 ID 和呈现状态。只存去重与频率所需元数据，不存聊天、天气整页或精确坐标。

记录表需对 delivery ID 和已展示事件键做唯一约束，并支持滚动 24 小时计数。事件键的唯一约束作用于已展示状态；同一事件确定未展示而取消后，不应被一条历史 reservation 永久阻塞，可使用条件唯一索引或独立去重表实现。`uncertain` 使用独立抑制期限，不能按正常已展示次数伪造回执。关怀候选和原始天气不作为可恢复任务保存。

### 12.3 回执、崩溃与记录失败

正常计次以 `care-presented` 为准。发出 offer 前可保存一条未计次的短期呈现 reservation；显示回执后事务转为 `shown`。重启遗留 reservation 标记为 `uncertain`，不重放，保守抑制该事件在当前窗口内再发。

不宣称跨崩溃绝对 exactly-once：若已经显示但回执未保存，优先避免重复打扰。未显示且确定取消的 reservation 不计已展示次数，仍遵守安静期。

记录库不可用或无法可靠登记时暂停自动关怀，普通聊天和环境读取继续；不因为写入失败而每次重新提醒。已展示记录保留至少 48 小时，节日/夜间事件键保留其有效窗口和清理余量；过期清理不能删除仍用于冷却的记录。

### 12.4 位置数据的保存与使用范围

固定/备用城市和 IP 城市确认记录可以持久保存；设备精确坐标、原始 IP 位置响应和移动历史不落盘。设备坐标仅在环境服务内存中按有效期保存，关闭来源时撤销使用资格并清理；重启后重新获取，不把旧坐标恢复成当前位置。

天气来源需要坐标时，只向选定的天气服务发送必要的查询坐标；城市解析若需要外部服务，其目的、传输字段与 HTTPS 要求也须在 A 阶段明确。首版不为展示精确地址额外引入逆地理编码服务。

聊天、模型、Hindsight 和普通前端订阅仅取得城市/地区、来源、天气和数据时间，不取得精确坐标或原始位置响应。设置/诊断页只展示精度范围与地区，不默认展示精确坐标；ledger 的地点键使用城市标识或规范天气区域键，不使用原始经纬度字符串。

## 13. 前后端接口和事件

后端新增命令建议：

- `environment_get_snapshot`：本地允许窗口读取，返回版本化快照。
- `environment_refresh_weather`：设置/调试窗口可请求，仍遵守开关、合并和最短间隔。
- `environment_request_location_access`：仅前台设置窗口在明确用户操作后调用，在 UI 线程发起系统访问申请；不能由任意渲染器或定时器触发。访问结果仍按当时配置版本校验。
- `environment_refresh_location`：设置/调试窗口请求按当前模式更新位置，只使用已有允许来源，不重复弹系统授权；合并同源请求并遵守最短间隔。
- `environment_confirm_ip_city`：仅设置窗口可确认最新估计的规范城市及候选代次；不接受前端自行提供的坐标、精度或 `confirmed=true` 覆盖事实。
- `environment_save_settings`、`care_save_settings`：仅设置窗口可写。
- `care_get_status`：返回开关、受限原因、当前是否允许关怀等，不返回聊天内容。
- `care_interaction_activity`：仅输入窗口可续编辑活动租约，不接受任意 draft 文本。
- `care_presented` / `care_rejected` / `care_finished`：仅当前渲染窗口可提交，校验 delivery 和代次，不信任前端传入时间或计数。

复用或扩展 `environment-updated`，提供 `schema_version`、相关版本和有效性变化；前端用版本过滤乱序数据。不把所有新对象强塞进旧 `WeatherInfo`，前后端 DTO 统一定义和同步测试。

快照按读者提供投影：聊天/关怀使用经检查的环境事实，设置/调试获得来源与失败原因，平台适配器内部才可读取原始坐标。新增命令按 Tauri 窗口权限收窄，首次授权不得因模型输出或页面任意事件执行。旧 `refresh_location_info` 兼容入口也必须遵守模式和开关，不能保留强制 IP 请求旁路。

care 事件使用独立命名和所有权，不写用户输入窗口的 busy 状态。相同机制用于序列帧、Live2D、PngRemix、3D 等既有渲染窗口。

## 14. 故障和边界行为

- 刷新失败、观测时间未知、地点不可靠：保留可诊断记录，抑制天气关怀；时间和节日仍可工作。
- 设备定位被关闭、拒绝、超时、陈旧或精度不足：按自动模式允许的来源降级；固定模式不受设备失败影响。定位失败不进入模型生成链路，不使用户回复等待定位。
- 备用城市可用时：使用并标注备用城市，不同时查询 IP；备用城市的天气暂时获取失败也不触发 IP。
- IP 位置尚未确认或确认已因城市变化失配：只展示明确标记的预览，抑制当前天气事实及关怀；不把旧城市确认转移到新城市。
- 对应来源关闭或权限撤销：在途定位、天气和候选按相关代次失效；两种自动来源都关闭且没有有效城市时，天气相关功能不可用。
- 天气转晴：取消相关候选和待呈现租约；不把早上候选改成“今天早上下过雨”继续补发。
- 用户一直忙：候选过期，不积压消息；下一次使用新事实重新评估。
- 多次恢复、网络抖动：刷新合并及退避，不密集重试，不集中补发。
- 切换 Mod、隐藏或锁屏：立即撤销关怀，相关候选取消；显示恢复后经过安静期重评。
- 数据更新与显示竞争：后端版本及前端呈现版本共同阻止迟到结果。不存在对现实世界天气瞬时变化的完全同步保证，应以证据时效和发送前检查为验收边界。
- 日期变更：旧节日候选取消；深夜提醒按 night key 去重，而非零点重置。
- 日历覆盖不足：不祝福未知节日，不影响其他有效类别。
- 对话/配音状态回执失联：租约到期保守等待；不能持有永久 busy，也不能据失联回执覆盖用户气泡。

## 15. 必须覆盖的场景

### 15.1 早上下雨，下午晴

08:00 接收雨天观测，产生短候选；用户忙到候选过期。之后如果没有有效新数据，雨天触发直接不可用。15:00 即使旧缓存仍是雨，也不能触发；若新观测为晴，清除候选。只有下午新的合格雨天观测，才可能重新形成一个基于下午事实的候选。

### 15.2 下午获取了早上的数据

15:00 请求成功，但观测时间为 08:00。接收时间可以显示 15:00，数据仍为 stale，不刷新观测有效期，不触发任何“现在有雨”台词。

### 15.3 等待期间转晴或用户发送消息

抽中 90 秒延迟后，天气转晴即取消；用户提交消息立即取消。迟到 offer、预设音频和回执都不能让该消息重新出现。

### 15.4 午夜与节日

23:50 已提醒休息，00:10 不再次提醒同一夜间。节日当天没找到合适时机则不发送，次日不补发。重启不清除已展示去重记录。

### 15.5 固定城市与实际设备位置不同

用户选定固定城市上海，设备实际位于北京。固定模式只查询上海天气，不调用设备/IP 改写选择；台词和界面标明上海，不声称用户就在上海。固定城市天气请求失败时仍保留上海，不降级到北京。

### 15.6 自动来源逐级降级

自动模式中设备定位被拒绝，已设备用城市杭州，则采用杭州并标注来源，不发 IP 请求。没有有效备用城市、IP 开关开启时才请求 IP；两类开关均关闭且无备用城市则停止天气关怀，本机时间/节日不受影响。

### 15.7 IP 首次估计与网络城市变化

IP 首次估计为广州，设置可展示带粗略标记的天气预览，未确认时不得触发雨天台词。确认后须结合合格天气才能使用；网络切换后估计为深圳，广州的确认不适用，旧候选取消。确认旧代次的广州不能覆盖当前深圳估计。

### 15.8 关闭定位与迟到响应

设备或 IP 请求发出后关闭对应开关，立即取消使用资格并选择允许的备用来源。原请求稍后成功也不能更新当前位置、启动天气查询或复活候选。Windows 授权申请尚未完成时关闭设备开关，后续系统允许结果也不能自动启用桌宠定位。

### 15.9 移动、位置过期和坐标抖动

有效天气仍显示雨，但所依赖设备位置已满 30 分钟未更新，关怀不可继续沿用该依据；先更新或采用合格备用来源。同一规范天气区域内合格的新位置记录仅更新年龄，不反复生成雨天事件；移动到另一查询区域后旧天气与候选失效，等待新区域的合格资料。

## 16. 实施阶段和交付门槛

### A：先统一数据及修复旧入口

1. 定义 Clock、地点/定位记录、天气、日历和有效性 DTO 及独立配置，先实现固定/自动模式与确定性的来源选择策略。
2. 注册 EnvironmentService，建立单一刷新生命周期、超时、退避、地点/配置版本及过期通知；接入城市目录、Windows 定位和满足 HTTPS 要求的 IP 适配器。
3. 完成前台授权、两个来源开关、固定/备用城市、IP 确认及来源状态展示。验证关闭/撤权使在途结果失效，未获允许时无后台定位旁路。
4. 核实当前天气源的坐标查询、实际区域匹配、时间解析与观测年龄；确定天气区域稳定映射和位置参数，整理核对 2026–2030 节日表。不满足合同则标为不可用。
5. 迁移第 11.1 节全部读者及旧位置刷新入口，禁止裸缓存和强制 IP 旁路；修复调试刷新，确保模型上下文不包含精确坐标。
6. 离线验证来源优先级、位置/天气分别失败、过期、关闭竞态和地点切换；真实定位与来源测试单独显式执行，在 Windows 10/11 的目标 NSIS 安装形态核对权限、无定位设备、拒绝/撤权与恢复行为。记录实测范围，不宣称所有设备均可精确定位。
7. 完成本阶段门槛后即可验证“上午旧雨数据下午不能触发旧台词”，不依赖新 CareService。位置读取失败不得妨碍其余共享数据与旧天气有效性修复。

### B：再实现候选、有效期与去重

1. 实现规则、相关版本绑定、候选生命周期、全局/类别冷却与独立 ledger。
2. 使用可注入的 Clock、位置/天气适配器、权限状态、随机源和呈现接收器做确定性测试。
3. 先以不真正显示的测试接收器验证过期、地点变化、跨夜、限额及崩溃恢复。

### C：最后接入随机时机、台词和交互

1. 接入 InteractionSnapshot、输入编辑租约、CareLease 和前端所有权。
2. 接管 Ema 旧关怀触发，复用经核对的台词；新增节日台词和设置区。
3. 验证抢占、迟到事件、静音、切换角色、不同渲染器及可选本地配音。
4. 全部验收完成后开放总开关；发布说明写清受管旧关怀的变化和数据源限制。

不得以 C 阶段界面可用作为 A 阶段完成证明；不得把本次设计文档或先前搜索 API 测试当作天气实况验证。

## 17. 验收清单

- **ENV-01**：服务只注册和启动一次，所有天气读者共享相同来源及地点版本。
- **ENV-02**：30 分钟旧观测即使刚获取，也不能支持天气关怀或旧天气状态。
- **ENV-03**：没有新网络响应也能按年龄变 stale，并通知订阅者；读取时再次检查。
- **ENV-04**：未知、无日期、时区无法解析或明显未来观测不被伪造成当前时间。
- **ENV-05**：同地点并发刷新只请求一次；最短间隔、超时、响应上限和退避有效。
- **ENV-06**：旧地点或旧观测的迟到响应不覆盖新的权威数据。
- **ENV-07**：刷新失败不延寿，仍有效的数据与失效数据状态区分正确。
- **ENV-08**：休眠恢复、网络恢复、时区和时间跳变触发保守核验，不补发周期。
- **ENV-09**：原命令、Mod 限制、AI 上下文和调试页均无裸缓存旁路，温度判断也受时效约束。
- **ENV-10**：未确认的 IP 估计不能支持当前天气事实或关怀；时区推算不进入天气位置链路；合格且获允许的设备位置按独立规则准入。
- **ENV-11**：日历数据有来源、版本、覆盖范围；越界或损坏不猜测春节或休假状态。
- **ENV-12**：当前时钟按使用时读取，跨日、跨午夜和时区变化自洽。
- **LOC-01**：固定模式只使用指定城市，不被设备/IP 覆盖；固定城市无效时不暗改模式。
- **LOC-02**：自动模式严格按合格设备位置、有效备用城市、获允许的 IP 依次选择；前项可用时不额外请求后项。
- **LOC-03**：已确定城市的天气请求失败不触发位置降级或城市切换。
- **LOC-04**：首次配置设备与 IP 开关均关闭；旧缓存不冒充手动城市或已确认位置；设置不依赖 AI 配置。
- **LOC-05**：系统访问申请仅由前台设置操作发起并遵守 UI 线程要求；拒绝后定时器不反复申请。
- **LOC-06**：应用设备开关与系统访问状态分离；关闭/撤权立即撤销使用资格，迟到授权或位置结果不能重新启用来源。
- **LOC-07**：IP 开关独立执行，关闭后无新增 IP 请求或旧结果提交；固定模式与网络天气关闭时无隐式周期查询。
- **LOC-08**：位置时间、接收年龄和水平精度均被核验；旧位置重收不延寿，边界值与未来时间行为确定。
- **LOC-09**：设备查询使用合格坐标并核对天气实际区域；城市中心与 IP 坐标不伪装为设备测量精度。
- **LOC-10**：IP 首次/换城须确认，确认绑定规范城市及当前候选；未确认仅可提供带标记预览，不进入当前天气合同。
- **LOC-11**：位置到期/切换导致依赖关怀失效；同区域坐标抖动不反复清天气或重建事件。
- **LOC-12**：所有位置来源受合并、超时、退避和配置代次约束；没有位置时聊天与环境读取快速返回，不等待网络。
- **LOC-13**：来源全部不可用时无时区坐标兜底；时间、日历和普通聊天继续工作。
- **LOC-14**：精确坐标仅在必要内存及天气查询中使用，不写配置、日志、ledger、聊天、模型或 Hindsight；无移动轨迹。
- **LOC-15**：IP 与天气网络请求满足 HTTPS、超时和响应上限；不合格 IP 实现不得作为上线兜底。
- **LOC-16**：真实 Windows 验证通过显式测试入口执行，并记录 NSIS 安装形态、权限/无定位设备/恢复结果；默认测试使用替身，不实际定位。
- **CARE-01**：候选有固定有效期与事实依据，不跨重启恢复，不无限排队。
- **CARE-02**：上午候选下午不会展示；新接收的旧观测也不能重建有效雨天候选。
- **CARE-03**：每候选只抽一次随机延迟；延迟和已知冷却超出有效期时放弃。
- **CARE-04**：同观测不能反复重建候选；当天雨天一次、8 小时冷却及全局限额有效。
- **CARE-05**：发送前复核，天气转晴、地点变化或数据过期均取消。
- **CARE-06**：编辑、IME、主动请求、阅读和回复音频期间不开始关怀。
- **CARE-07**：用户提交与 offer 并发时用户优先；迟到文字、音频和回执不能复活 care。
- **CARE-08**：关怀不设置聊天 busy，不禁用发送、不清草稿、不抢焦点、不污染对话状态。
- **CARE-09**：夜间跨零点只提醒一次；节日结束不补发；重启不造成重复。
- **CARE-10**：展示回执幂等；未显示不计正常次数；崩溃 reservation 保守抑制而不重放。
- **CARE-11**：ledger 不可用时仅暂停关怀，环境服务与普通聊天仍能工作。
- **CARE-12**：新旧 Ema 关怀路径统一控制，不出现原雨天随机与新调度双发。
- **CARE-13**：关闭关怀后受管 Ema 台词不从旧路径绕过；普通动画和非关怀随机保留。
- **CARE-14**：没有模型、搜索或 TTS 凭据也能使用本地时间/节日预设关怀。
- **CARE-15**：台词不声称用户疲劳、连续工作、正在出门或今天必然放假。
- **CARE-16**：全局静音、免打扰、隐藏、锁屏及 Mod 切换符合边界；音频所有权隔离。
- **CARE-17**：care 不伪造用户消息，不作为 screen 来源或用户事实写入记忆。
- **CARE-18**：设置及记录迁移不改变既有对话 schema、bank、凭据或其他设计稿字段。
- **CARE-19**：离线测试用虚拟时钟和固定随机种子，不实际等待数小时、不访问真实密钥或远端源。
- **CARE-20**：按 A→B→C 逐阶段验收；最终运行现有输入、长回复、语音和渲染回归检查。

## 18. 文件分工、诊断及参考

### 18.1 建议文件分工

新增 `modules/environment_service/`：`mod.rs`、`types.rs`、`clock.rs`、`location.rs`、`weather.rs`、`calendar.rs`、`settings.rs`；`location.rs` 拆分来源选择、城市目录和 `providers/windows_location.rs` / `providers/ip_location.rs` 等平台适配器。新增版本化年度日历资源。旧 `environment.rs` 的纯时间/日期帮助函数可复用，网络与缓存所有权迁入服务。

新增 `modules/care/`：`mod.rs`、`types.rs`、`rules.rs`、`scheduler.rs`、`ledger.rs`、`settings.rs`；新增本地文本目录及经核对的音频映射。

修改 `modules/mod.rs`、`lib.rs`、必要的 `lib_helpers.rs`、`commands/mod.rs`，增加受限环境/关怀命令模块；迁移 `state.rs` / `state_runtime.rs` 和 `companion/capabilities.rs`。

Windows 依赖 feature 和必要初始化改动限定在平台适配范围，按实际安装形态核对系统要求；Tauri capability 限制设置命令来源，不能代替系统定位访问检查。

前端新增环境与关怀共享类型、设置区和 `care/presentation.ts`；修改输入框活动回执、`WindowCore.ts`、必要的音频所有权协调和 `EnvironmentDebugger.svelte`。不要把关怀后台过程塞进现有用户聊天组件。

### 18.2 诊断与验证

固定事件名、枚举结果、相关代次及耗时可以记录；不记录聊天、按键、精确坐标或完整天气响应。设置/调试页显示天气年龄、不可用原因和被抑制的关怀原因，便于区分“随机尚未到时机”“用户忙”“资料过期”。

位置诊断补充模式、实际来源、是否采用备用城市、位置年龄、精度范围、系统访问状态与降级原因。性能验证分开记录授权等待、位置读取和天气耗时；不得把异步刷新加入用户每轮回复的等待链。

真实源验证单独显式执行，至少记录观测年龄、接收时间、地点绑定、成功率和恢复行为。测试数据不足以支持 30 分钟合同，就不能宣称天气关怀已经可靠。

### 18.3 与其他功能的边界

本稿服务不依赖网页搜索，关怀不触发搜索。既有对话、屏幕和长上下文设计可消费其环境快照，但不得重建一份无时效判断的天气缓存。独立配置及 ledger 不占用这些设计已约定的 schema 版本。
